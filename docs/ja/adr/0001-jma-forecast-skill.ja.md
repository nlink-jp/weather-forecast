# ADR-0001: weather-forecast スキル — 気象庁の予報を決定的スクリプトで整形し、モデルは読むだけにする

| 項目 | 値 |
|------|-----|
| 状態 | **承認** |
| 日付 | 2026-10-09 |
| 拘束範囲 | weather-forecast |
| 決定者 | nlink-jp メンテナ |
| 契機 | 「天気予報を調べるスキル」の依頼。先行の weather-lens（気象庁ソースのメニューバーアプリ）は 2026-08-13 に UX 不良で中止している |

## 背景

日本国内の天気予報を会話の中で聞けるようにしたい。要件は利用者との合意で次のとおり確定した。

- データ源は**気象庁のみ**（国内のみ・公式・API キー不要）
- 答える内容は**今日〜明後日の予報**、**週間予報**、**天気概況（気象台の解説文）**
- **警報・注意報は扱わない**。聞かれたら気象庁の警報ページを案内する

気象庁の `www.jma.go.jp/bosai/` 配下の JSON は公式サイト自身が読んでいるデータで、それ自体の
API 文書は無い。ただし中身は気象庁防災情報 XML と同じ予報であり、その**解説資料**
（https://xml.kishou.go.jp/tec_material.html の「解説資料セット」）が要素の意味を定めている。
設計は解説資料に拠り、資料が黙っている JSON の形は実データの観測で確定した
（CONVENTIONS「Design from the documentation」）。bosai JSON と XML の対応は、17 時発表の
気温の時刻が資料の枠と一致することなどから推定したもので、文書で保証されたものではない。

### 文書で確認した事実

解説資料セット（2026-08-26 版）の「府県天気予報，地域時系列予報（Ｒ１）_解説資料」
「府県週間天気予報_解説資料」「府県天気予報・府県週間天気予報_解説資料付録.xlsx」による。

1. **気温の枠は最大 4 つ**: 「今日日中」（今日 9 時、日中の最高気温）、「今日」（今日 0 時から
   24 時間、最高気温）、「明日朝」（明日 0 時、朝の最低気温）、「明日日中」（明日 9 時、日中の
   最高気温）。発表時刻によって「今日」「今日日中」が省かれる。**今日の朝の最低気温という枠は無い。**
2. **天気予報用テロップ番号の表は公式にある**（付録のシート「天気予報用テロップ番号」、66 件、
   「晴れ時々くもり」のように詳細予報の文字列と同じ書き方）。
3. **週間予報の明日・明後日の信頼度は発表しない**。明日の降水確率と気温は府県天気予報が受け持つ。
   空値は欠損ではなく「この情報では出さない」という意味。
4. **警報・注意報の種別名の表も公式にある**（コード管理表の「警報等情報要素コード管理表」。
   2024-10-31 の R06 対応で更新済み。weather-lens が「公表資料に無い」としたコードも載っている）。

### 観測した事実（2026-10-09 未明、58 の府県予報区すべて、17 時発表 1 回分）

1. **58 区中 2 区は自前の予報ファイルを持たない。** 十勝地方 `014030` と奄美地方 `460040` は
   `forecast/data/forecast/{code}.json` が 404 で、それぞれ `014100`（釧路・根室）と
   `460100`（鹿児島）のファイルに同居している。概況も同じで、同居先の概況は両地域を含む。
2. **予報 JSON の構成は全区で同じ**: 配列の 0 番が明後日までの詳細（天気・風・波 / 6 時間
   降水確率 / 気温）、1 番が 7 日分の週間予報。区域数が違い、海に面しない 8 県には `waves` が無い。
3. **週間予報には天気の文字列が無く、テロップ番号だけがある。** 公式予報ページの HTML には
   `TELOPS` 表（118 件）が埋め込まれており、公式表の 66 件をすべて含む（名称は「晴時々曇」の
   ような略記）。第 3 欄はアイコンの分類で、番号の頭の桁とは 65 件で一致しない
   （102「晴一時雨」は雨の分類）。
4. **発表時刻は一定でない。** 詳細予報は 5・11・17 時が基本だが、宮城・福島は 20:00 発表だった。
   詳細と週間は発表時刻が別に記録され、概況はさらに別（分単位）。
5. **深夜は「今日」がずれる。** 10/9 3 時に取れる最新は 10/8 17 時発表で、詳細予報の先頭は
   10/8 の夜。公式ページは発表時点を基準に「今夜 08日」と表示し続ける。
6. **空値は空文字で来る**（週間予報の最初の 1〜2 日の気温・信頼度・降水確率）。
7. **週間予報の行は府県単位。** 公式の `week_area.json` は地域ごとの**候補の並び**で、その時の
   データに実在するものだけが有効。142 地域中、候補が当たるのは 64 地域。当たらない 78 地域の
   うち 74 は週間予報が 1 行しかない府県にあり自明で、決められないのは 4 地域（伊豆諸島北部、
   下北、沿岸南部、浜通り）。公式ページも地域ごとの対応付けはせず、
   府県の全行を地域名つきで並べる。
8. **週間予報の気温行は天気行と同じ順に並ぶ**（全 63 行、`week_area.json` の組とも一致）。
9. **詳細予報の気温地点**は `forecast_area.json` に地域ごとの候補として並び、現在のデータに
   無い地点も含む（`63576`、`73136`）。

## 決定

**skills-series に `weather-forecast` スキルを追加する。取得・地名解決・整形は同梱の
Python スクリプト（標準ライブラリのみ）が決定的に行い、モデルは整形済み JSON から答えを書くだけにする。**

### 1. モデルに生データを読ませない

上のとおり「読み方の層」が厚い（数値コード、区域と地点の二重体系、空文字、候補リスト、
発表時点基準の日付、枠ごとに意味の違う気温）。どれも誤読してもエラーにならず、もっともらしい
天気として返ってくる。読み方はスクリプトに閉じ込め、テストで固定する。モデルの判断は
「地名の候補が複数あるときに聞き返す」「どの期間を答えるか選ぶ」「文章にする」に限る。

### 2. スクリプトの面

`scripts/jma_forecast.py` 1 本、2 つのサブコマンド。

- `resolve <地名>` — `area.json` の 4 階層（府県予報区・一次細分区域・二次細分のまとまり・
  市町村等 1,805 件）の名前を引き、候補ごとに「府県予報区・一次細分区域」の組を返す。
  並びは完全一致 → 前方一致 → 部分一致で、完全一致か前方一致が 1 つでもあれば部分一致だけの候補は
  落とす（「京都」で東京都を出さない）。同じ府県予報区の全域と一次細分区域が両方残ったら、
  全域は名前が完全一致したときだけ残す（「東京」は東京地方、「東京都」は全域）。地方名（`centers`、
  「東北」「九州」）も同じ順位付けに入れ、配下の府県予報区を候補にする（東北町だけで「東北」に
  答えない）。名前の比較は NFKC に加えて ヶ/ヵ を ケ/カ に寄せる（area.json 自体が龍ケ崎市と
  茅ヶ崎市を混用している）。候補が複数ならすべて返し、選ぶのはモデル（利用者に聞き返す）。
  子地域が 1 つだけの府県予報区はその子地域と同一に扱う。
- `forecast --office <コード> [--area <コード>]` — 区域コードは階層をまたいで重複する
  （`014030` は府県予報区でも一次細分区域でもある）ので、2 つを別の引数で受ける。どちらも
  `area.json` に実在しなければ URL を組み立てる前に拒否する。

実行時に取得するのは気象庁の `area.json`・`forecast_area.json`・`week_area.json`・予報・概況の
5 本。キャッシュはしない。**どれか 1 本でも失敗したら全体を失敗にする**（`fetch_failed`、終了コード 2）。
一部だけ欠けた結果を返すと、モデルは欠けた節を「その情報は無い」と読んで答えてしまう。
想定外の形のデータ（JSON でない、配列が空、週間予報の天気行と気温行の数が違う等）は
`bad_response` とし、どの失敗も traceback ではなく JSON で返す。時差の無い時刻は日本時間として読む。

### 3. 日付は現在の日本時間で付け直す

各枠に実際の日付と、現在の日本時間から見た相対ラベル（今日・明日・明後日）を付け、過ぎた日と
終わった 6 時間枠（終わりが現在時刻以前）は落とす。現在時刻は `--now` で差し替えられる（テスト用）。

### 4. 気温は文書の枠で読む

9 時の値は日中の最高気温として読む。0 時の値は、**0 時の枠が 2 つあればその後ろの方だけ**を
朝の最低気温として読み、前の方（「今日」24 時間の最高気温）は最低気温として読まない。0 時の枠が
1 つなら（17 時・20 時発表）それが朝の最低気温。発表日ではなく枠の並びで決めるので、日付が
変わってから出た訂正でも読み違えない。地点は `forecast_area.json` の候補の
うち、現在のデータにある最初のものを使う。

### 5. 週間予報は府県の全行を名前つきで出す

公式ページと同じく府県の週間予報の全行を地域名つきで出し、`week_area.json` の候補が現在の
データに当たったときだけその行に `matched: true` を付ける。決められない地域では、モデルは行の
地域名をそのまま示して答える（推測で 1 行に決めない）。気温は同じ順の行を使う。
同居ファイルの府県では、`week_area.json` に載る自府県の行だけを出す（鹿児島に奄美の行を出さない）。

### 6. テロップ番号は公式表を優先し、ページの表で補う

`scripts/telops.json` に、公式表（66 件、資料名とシート名つき）と予報ページの `TELOPS` 表（118 件）の
写しを、取得日つきで同梱する。引くときは公式表を優先し、公式表に無い番号はページの表で補う。
保守コマンド `make sync-telops` が予報ページと突き合わせ、公式表は解説資料の新版が出たときに
`--appendix` で取り込む。

**どちらの表にも無い番号は名称を `null` にし、推測しない。** 番号の頭の桁は最初の天気しか
表さず（1xx は「晴」で始まる）、「晴一時雨」を「晴」と答えることになる。答えでは天気の語を出さず、
降水確率と気温だけを示す。**番号そのもの・「表に無い」という説明は答えに出さない。** weather-lens は
上流に無い名称を「コード＋出せない理由」で埋めて UI を実装事情に支配させ、中止に至った。
出力 JSON の週間予報にも番号は含めない。

### 7. 同居ファイルの対応は明示の表で持つ

`014030 → 014100`、`460040 → 460100` をスクリプト内の表で持つ。実行時に 404 を見てから探す方式は
採らない（失敗経路が通常経路になり、取得回数も読めなくなる）。

### 8. 鮮度は詳細予報の発表時刻で判定する

詳細予報の発表時刻が現在から **15 時間**より古ければ `stale: true` を付ける。詳細予報の定時発表の
間隔は最大 12 時間（17 時 → 翌 5 時）で、観測した更新はいずれも定時より前だった。週間予報の発表
間隔は解説資料に書かれておらず未確認（詳細予報より長ければ、朝に誤って古いと判定する）なので、
判定には使わない。詳細・週間・概況の発表時刻はそれぞれ出力に含め、
答えでは答えに使った部分の発表時刻を添える。廃止されたエンドポイントが 200 で古いデータを返し
続けた前例（警報の旧パス、2026-05-28 で凍結）があるため、疎通ではなく鮮度で見る。

### 9. 警報・注意報は扱わない

利用者との合意による範囲の決定。聞かれたら気象庁の警報ページの URL を案内する。
なお、合意の際に「種別名の表は公開されていない」と説明したが、これは誤りだった（文書で確認した
事実 4）。表は公開されているので、警報は将来の版で範囲に入れうる。その場合は、表の写しと保守
コマンドで名称を自前で持つ（テロップと同じ形）ことが前提になる。

### 10. 答えには出典と加工の旨を必ず添える

気象庁ホームページのコンテンツは公共データ利用規約（第1.0版）で利用でき、出典の記載と、
編集・加工した場合はその旨の記載が求められる。スクリプトの出力に出典の文言（予報ページの URL つき）
を含め、SKILL.md で答えの末尾にそのまま添えさせる。形は「出典：気象庁ホームページ（URL）を加工して作成」。

## 影響

- 動作環境は、スキルが `python3` を実行でき `www.jma.go.jp` へ接続できる場所。Claude Code
  （デスクトップアプリの Code タブと CLI）は満たす。デスクトップアプリに登録したスキルは
  チャットからも呼ばれうるが、チャットの実行環境から気象庁に届くかは**未実測**。
- テストは記録した実データを固定データとして同梱し、本番と同じ取得経路（URL の基点を
  `file://` に差し替える）でネットに繋がず `make check` で走る。
- 固定データは 10/8 17 時発表と 10/9 5 時発表の全区。5 時発表では気温の枠が全 56 ファイルで
  4 つ（今日 9 時・今日 0 時・明日 0 時・明日 9 時）あり、今日 0 時の値は全 171 地点で今日 9 時の値と
  同じだった（文書どおり「今日」は最高気温）。詳細予報は今日・明日の 2 日分、週間予報は前日 17 時
  発表のままで、1 区は 8 時の臨時発表だった。11 時発表と、雨や雪の多い日のデータは手に入りしだい加える。
- 気象庁が構造や表を変えても、オフラインのテストは通り続ける。変化に気付く手段は
  `make check-upstream`（全区の同居ファイル・構成・鮮度・テロップ名・気温地点）と
  `make sync-telops` で、**リリース前に必ず実行する**（AGENTS.md のリリース手順）。
- 受け入れた残余のリスク: 取得サイズの上限は設けない（配信元が気象庁であり、タイムアウトは
  20 秒）。概況の自由文は気象台の文章としてそのままモデルに渡す。SKILL.md の
  `allowed-tools: Bash(python3 *)` は同梱スクリプト以外の python3 実行も許すが、インストール先の
  パスが登録方法で変わるため絞れない（組織の他スキルと同じ形）。

## 検討した代替案

- **モデルに `WebFetch` 等で JSON を読ませる。** 手順を SKILL.md に書くだけで済むが、読み方の層を
  毎回モデルに推論させることになり、誤読がテストで捕まらない。
- **Open-Meteo の併用・単独。** 海外に答えられるが、国内でも気象庁の公式予報ではなく数値モデル
  由来の値になる。要件から外した。
- **テロップ表を実行時に公式ページから抽出する。** 常に最新だが、圧縮済み JavaScript の抽出が
  質問のたびに走り、ページの書き換えで答えが壊れる。写し＋保守コマンドの方が壊れ方が見える。
- **表に無い番号を頭の桁から名付ける。** 当初案。番号の頭の桁は主な天気だけを表し、降水を含む
  天気を「晴」と答えることになるので採らなかった。
- **週間予報を地域ごとに 1 行へ決め打つ。** 決められない 4 地域で推測になる。公式ページもしていない。
- **一部の取得が失敗しても残りで答える。** 欠けた節をモデルが「情報が無い」と読むため採らなかった。
- **アメダスの現在値。** 欠測と品質フラグの扱いが加わる。要件から外した。
